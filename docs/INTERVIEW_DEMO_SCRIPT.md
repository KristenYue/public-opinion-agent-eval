# 3 分钟面试 Demo 讲解稿

这个版本同时讲清“业务 Agent 为什么有用”和“它为什么具备生产工程可信度”。在线 V1 Demo 用于展示业务决策；V2 Job/Trace、CI 和架构图用于展示异步执行、恢复与审计，不把两者混成同一部署证据。

在线地址：[ModelScope 舆情研判 Agent](https://modelscope.cn/studios/KristenYue/public-opinion-agent-demo)

## 演示前准备

按以下顺序打开四个标签页：

1. 在线 `/console` 或仓库内离线演示视频 `docs/舆情研判Agent_3分钟离线演示.mp4`；
2. [最终架构图](ARCHITECTURE.md)；
3. 本地/部署环境的 `/trace` 页面；若现场没有 PostgreSQL/Redis，则改用 PR `#4` 的绿色 CI 和 [V2 API 文档](V2_API.md)，不要伪造实时任务；
4. [Benchmark v1.5 最终结果](BENCHMARK_V1_5_RESULTS.md)。

预先准备一个只含公开合成评论的 Job ID。不要展示真实用户数据、API Key、数据库密码或 `.env`。如果没有可运行 V2 环境，明确说 Trace 已由 PostgreSQL/Redis CI 验证，现场展示的是文档与测试证据。

## 三分钟操作与逐字稿

### 0:00–0:25　问题与定位

操作：停留在研判控制台输入区。

> 这是我把本科情感分析毕设重构成的可复核舆情研判 Agent。旧模型在原分布内有效，但换到新事件、反讽和依赖上下文的短评论时会高置信出错。因此我没有只换一个更大的模型，而是围绕错误识别、分级路由、人工接管、失败关闭和全链路审计重建系统。

### 0:25–0:55　业务决策路径

操作：载入公开示例并运行，指向情绪结构、复核队列和证据。

> 输入包含事件目标、上下文和评论。XGBoost 提供低成本基线，SnowNLP 是第二信号；模型分歧、不可评分和短文本上下文风险会触发结构化 Reviewer。只有满足采用门禁才覆盖基线，否则进入 `manual_required`。历史事件检索只提供带来源的上下文，不被包装成因果证明。

### 0:55–1:20　为什么是 Agent

操作：切换“工具轨迹”或指向架构中的 Agent 决策图。

> 它不是自由发挥的聊天机器人，而是边界受控的 Agent。运行时状态和工具结果会改变后续路径：快速放行、检索、升级复核、受控覆盖或转人工。每次节点状态、路由原因、工具耗时、证据来源和降级结果都能追溯，所以系统可以拒绝不确定结论，而不是永远返回一个看似完整的答案。

### 1:20–1:50　Production V2

操作：切到最终架构图，沿 `POST /v2/jobs → PostgreSQL → Redis/ARQ → Worker` 指示。

> V2 保留同步 Demo，同时增加幂等异步 Job。API 先把脱敏请求持久化，再入 Redis 队列；Worker 通过原子 claim、lease 和 heartbeat 防止重复执行。每次尝试开始前固化模型、Prompt、工具和策略版本，并保存带哈希的输入 checkpoint。Worker 崩溃或租约过期时，新尝试从输入 checkpoint 重放；旧 Worker 不能覆盖新所有者的结果。

### 1:50–2:15　Trace、恢复与 Shadow 隔离

操作：在 `/trace` 输入合成 Job ID，指出状态、恢复次数、失败原因、Run、checkpoint、tool call 和 Shadow 卡片。

> 这个页面不是内存日志，而是 PostgreSQL 审计账本的读取模型。它按 attempt 展示正式 Run、恢复原因、检查点和工具调用。`manual_required` 表示暂停自动结论等待人工，不冒充任意节点暂停。Runtime candidate 默认关闭；启用时只写独立 `shadow_runs`，即使超时或失败也不能改写正式 Job。

### 2:15–2:42　评测与工程证据

操作：切到 Benchmark 结果和 GitHub Actions。

> 业务评测使用 599 条、12 个事件的数据，并按事件隔离。6 个未见事件、339 条评论上的 XGBoost 基线 Accuracy 是 31.27%，事件感知纯自动流程是 56.05%；系统自动处理 78.76% 样本时，选择性 Accuracy 是 66.67%。另外，CI 串联 RAG、安全故障注入和 60 对 Runtime 回归门禁，并在真实 PostgreSQL 16、Redis 7 上验证迁移、任务生命周期、Trace 读回和 Shadow 隔离。

### 2:42–3:00　结论与边界

> 完整工作流 73.75% 包含 21.24% 人工接管，所以我不会称它为模型准确率；Runtime 的延迟和成本也只是合成契约校准，不是生产 SLA。这个项目的核心不是堆模型，而是证明：不可靠组件可以被路由、约束、恢复、审计，并在证据不足时安全地把决定交还给人。

## 演示口径速查

| 指标或能力 | 正确表述 | 禁止表述 |

| 339 / 6 | 最终测试评论数 / 未见事件数 | 随机切分测试 |
| 31.27% | XGBoost 跨事件基线 Accuracy | 当前最终模型效果 |

| 21.24% | 人工介入率 | 模型失败率 |
| 73.75% | 自动结果加人工兜底后的工作流结果 | 模型准确率 |
| 60 对 Runtime case | 合成契约回归门禁 | 生产 SLA 或真实成本 |
| `manual_required` | 暂停自动结论等待人工 | 任意 LangGraph 节点暂停 |
| input checkpoint replay | 从输入重放恢复 | 节点级续跑 |

## 页面或环境异常时

### 在线 Reviewer 没有 API Key

> 公开 Demo 不暴露 API Key。预置示例可以使用明确标识的冻结验收回放；自由输入若无法取得可信 Reviewer 结果，就进入人工复核，不伪造大模型输出。

### ModelScope 冷启动

> 在线空间正在冷启动。我先用离线演示视频和最终架构说明业务路径；仓库保留相同 API、冻结评测和自动化测试。

### 现场没有 PostgreSQL、Redis 或 Docker

> 我不把无法运行的本机环境说成已验证。V2 的真实服务证据来自 PR `#4`：PostgreSQL/Redis integration 应用全部 migration，并验证正式 Trace 和隔离 Shadow 读回；这里用 API 文档和绿色日志说明相同契约。

### 面试官要求随意输入一句话

> 可以，但请同时提供事件目标和背景，因为项目判断的是评论相对于目标的立场，不是脱离语境猜情绪。新评论会按严格策略复核；证据不足时显示待人工确认。

## 高频追问

### 为什么不全部调用大模型？

成本、延迟、可用性和有害覆盖风险都需要控制。小模型处理明确样本，大模型只复核争议样本，低置信结果继续交给人工。

### 为什么保留准确率不高的 XGBoost？

它是可解释、低成本的基线信号，不是最终裁决者。系统显式识别它在分布外的失效，并用路由限制错误外溢。

### 为什么不直接使用 Runtime Platform 作为正式执行器？

先以默认关闭的 Shadow 路径验证适配器、隔离和回归门禁，避免未验证候选直接影响正式结果。只有真实流量证据和发布策略成熟后才讨论切换。

### 这是 Agent 还是普通流水线？

它是受控 Agent 工作流：运行时状态和工具结果决定后续路径，同时工具、预算、输出合同和人工边界预先受控。高风险业务需要的是可约束自治，不是无限制自主规划。

### 下一步是什么？

先完成 Docker image 与完整 Compose smoke test、认证授权边界和更多独立事件数据，再考虑通信故障诊断扩展；不优先增加 Multi-Agent 复杂度。
